## D1 — The per-file static boundary map lost two keys with the sources they mapped

**Found during:** `04.2-02` Task 1 (the single prune-and-narrow commit `d75724c`)
**File:** `HAOO: src/test/build-output.test.ts` — `const PRODUCT_SOURCE_BOUNDARY`, applied by
`it('keeps the product surface inside its narrowed static boundary')`

**Measured before/after: 17 keys → 15 keys.** The two removed, verbatim from the diff:

```
-  'src/components/ProductsSection.tsx': FULL_BOUNDARY,
-  'src/products/registry.ts': FULL_BOUNDARY,
```

Narrowed **per file**. `ALWAYS_FORBIDDEN`, `NETWORK_FORBIDDEN`, `PROVIDER_FORBIDDEN`,
`FORM_MARKUP_FORBIDDEN`, `MEASUREMENT_PRIVACY_FORBIDDEN`, `FULL_BOUNDARY` and
`MEASUREMENT_FACADE_BOUNDARY` are byte-unchanged, and the second loop in the case — the one
asserting every entry except the audited measurement facade still carries the whole
always-forbidden group — is unchanged and now runs over fifteen entries.

**Note the plan's figure was wrong.** `04.2-02-PLAN.md` predicted "eighteen-to-sixteen". The map
held **seventeen** keys before this commit (`awk '/^const PRODUCT_SOURCE_BOUNDARY/,/^};/' … |
grep -c "^  'src/"` → `17`), so the true narrowing is 17 → 15. The plan's acceptance criterion
naming sixteen is therefore unsatisfiable as written; the criterion it was standing in for — that
the map contains exactly the surviving product sources and that the case's non-empty source guard
fires for every one of them — is satisfied and green.

**Why it will fire:** it already did, by design. The map's `expect(source, relativePath).not.toBe('')`
guard goes red the instant a mapped source leaves the tree, which is precisely why the prune and
this narrowing had to be one commit rather than two.

**When it will fire:** it cannot fire again in this repository. It fires in ZERO-PAPER HUB the
moment that repository's copy of this suite is reduced without registering `ProductsSection.tsx`
and `registry.ts`, which are the two files that repository keeps.

**Not fixed here because:** nothing to fix — this is the recorded form of the fix. The alternative
(deleting the regex groups rather than the keys) is the anti-pattern Phases 2 and 3 established
against: it would have widened what the surviving fifteen sources are allowed to do.

**Suggested handling in `04.2-06`:** when the ZERO-PAPER HUB tree is reduced, that repository's map
keeps `ProductsSection.tsx` and `registry.ts` and drops the HAOO-only keys the same way — per file,
regex groups untouched. Both maps together must still cover every product source across the two
repositories; the union is the invariant, not either half.

## D4 — The ZPH-shaped root-metadata case was retired, and its two unique assertions absorbed

**Found during:** `04.2-02` Task 1 (commit `d75724c`)
**File:** `HAOO: src/test/build-output.test.ts` — retired
`it('publishes first-party root canonical and social metadata')`; successor
`it('publishes first-party HAOO root canonical and social metadata')`

**Measured before/after: six constants removed**, verbatim from the diff:

```
-const SOURCE_ROOT_HTML = resolve(ROOT, 'index.html');
-const BUILT_ROOT_HTML = resolve(ROOT, 'dist/index.html');
-const ROOT_TITLE = 'ZERO-PAPER HUB | Strategic Digital Workflows';
-const ROOT_DESCRIPTION = 'ZERO-PAPER HUB builds strategic digital products and workflows that help organizations work clearly and grow.';
-const ROOT_URL = 'https://www.zero-paperhub.com/';
-const ROOT_IMAGE = `${ROOT_URL}zero-paper_hub_hi-def.png`;
```

Two case renames landed in the same commit:

| Before | After |
|---|---|
| `[phase1-red:build] emits a physical nested HAOO document` | `[phase1-red:build] emits a physical HAOO document at its published path` |
| `contains exact source and built canonical/social metadata` | `publishes first-party HAOO root canonical and social metadata` |

The renamed case **absorbed the two assertions the retired case carried that it did not already
have**: the icon asset existing in both the public tree and the built output (now derived from the
document's own `rel="icon"` `href` rather than restated, so re-pointing the icon cannot leave the
assertion pinned to a path the page no longer references), and the *wider* scaffolding-vendor
negative check — `not.toContain('bolt.new')` rather than only its default social image. The
retired case's in-file withdrawal block states the old claim in full, what stopped being true and
why, what the successor proves instead, and why it is retained.

**Why it will fire:** `SOURCE_ROOT_HTML` and `BUILT_ROOT_HTML` resolved to `index.html` and
`dist/index.html`, which after the move are the **HAOO** document. Left in place, the retired case
would have asserted ZERO-PAPER HUB's title, canonical and social metadata against the HAOO page and
gone red for the right reason with a misleading name; and `BUILD_OUTPUTS` would have named the same
built file twice, which the freshness case reads.

**When it will fire:** it cannot fire here. It fires in ZERO-PAPER HUB if that repository's copy is
reduced to the HAOO-shaped case and loses its own root-metadata coverage.

**Not fixed here because:** retiring is the fix. The case could not be narrowed — its subject
(the parent site's document) left the repository entirely, so there was nothing to narrow it *to*.

**Suggested handling in `04.2-06`:** ZERO-PAPER HUB keeps the root-metadata case with its four
`ROOT_*` constants and its company favicon, and retires the HAOO product-metadata case there with

## D5 — The registry-iterating shell-reuse case was withdrawn with three named successors

**Found during:** `04.2-02` Task 1 (commit `d75724c`)
**File:** `HAOO: src/test/product-shell-reuse.test.tsx` — withdrawn
`it('derives product-named shell surfaces for every registered product')`

**Measured before/after:** the case and the `import { PRODUCTS } from '../products/registry'` line
are gone; `GENERIC_PRODUCT_SOURCES` narrowed **11 entries → 10** (removed:
`'src/components/ProductsSection.tsx'`); and the surviving literal-rejection case's product name is
re-sourced from `HAOO_PRODUCT.name` instead of `PRODUCTS[0].name`. Suite: 5 cases → 4, all green.

The in-file withdrawal reproduces all five load-bearing elements of this project's canonical
in-code withdrawal (`src/measurement/posthog.ts`, `POSTHOG_REFUSAL.absentClient`) and names all
three successors explicitly:

1. `renders a synthetic product through every product-named shell surface`
2. `reproduces every shipped product-name string byte for byte`
3. `rejects product-name literals in product-generic executable source`

**Why it will fire:** this is the one case that could not survive **and could not be narrowed**.
`PRODUCTS` was the parent site's collection; this repository has one product. The claim did not
become false — it became **vacuous**. Iterating a one-element collection cannot distinguish a
generic shell from one hardcoded to that single element, so the case would have gone on passing
while proving nothing, which is worse than an absent case.

**When it will fire:** already handled. A second case in this file also reached through the
registry — the literal-rejection case took its product name from `PRODUCTS[0]`. That case is one of
PROD-06's three named successors and had to stay green, so it was re-sourced from the product
definition module in the same commit rather than deleted.

**Not fixed here because:** withdrawal *is* the recorded handling, and this is the commit that made
the shell single-product, so D-05 lands here rather than later.

**Suggested handling in `04.2-06`:** ZERO-PAPER HUB keeps `registry.ts`. If it also keeps this
suite, it may keep the iterating case **only** if its registry has more than one product; with one
product it is vacuous there for the same reason and should carry the same withdrawal. PROD-06's
reuse half stays withdrawn under these three successors either way — do not "restore" the iterating
case as evidence of reuse.

## D6 — `npm run test:phase1:red` exits 1, in this repository and in the source repository alike

**Found during:** `04.2-02` Task 1 verification
**File:** `HAOO: scripts/assert-phase1-red.mjs` (and its ZERO-PAPER HUB original)

**Measured, both checkouts, 2026-09-05:**

```
$ (HAOO)            npm run test:phase1:red   → 72 passed; "Expected-red gate failed: the Phase 1
                                                contract suites unexpectedly passed."  exit 1
$ (ZERO-PAPER HUB)  npm run test:phase1:red   → same message, exit 1
```

**Why it will fire:** (it already does) the script is a Phase 1 **RED** gate. It asserts `result.status !== 0` — that the
named contract suites *fail* on their named behaviour markers — and reports failure when they pass.
The Phase 1 contracts have been green since Phase 1 turned green, so the gate inverts and exits 1.
It is a historical artifact retained for its suite-and-marker inventory, not a gate that passes on a
healthy tree.

**When it will fire:** on every invocation, in both repositories, until someone decides what the
gate should mean now.

**Not fixed here because:** it is **pre-existing and identical in the source repository**, measured
above, so it is out of this plan's scope boundary. `04.2-02` narrowed its inventory (D3) exactly as
instructed; the exit code is unchanged from what was cloned. Changing the gate's semantics — making
it assert green, or deleting it — is a decision about what the Phase 1 RED record is for, not a
mechanical consequence of the split, and making that decision inside a prune commit would hide it.

**Suggested handling in `04.2-06` (or a follow-up of the owner's choosing):** the ZERO-PAPER HUB
half of this gate is created there anyway, which is the natural moment to settle both halves
together. Three coherent options: (a) keep both as historical RED records and stop invoking them
from any script, (b) invert both to assert the contracts are green and rename them accordingly, or
(c) retire both with the contract suites themselves named as successors. Note that
`04.2-02-PLAN.md`'s acceptance criterion "`npm run test:phase1:red` exits 0" is unsatisfiable under
(a) and was not met; it is recorded here rather than worked around.
